# Reporting-Agent — Claude Notes

## Agent behaviour — no polling loops

Do not subscribe to PR activity and do not schedule self check-ins
(`send_later`, routines, `/loop`) unless I explicitly ask. This repo has no CI
that runs on `pull_request`, so there is nothing for a watcher to catch — open
the PR, tell me, and stop. If you think something genuinely needs watching, ask
first and say what signal you expect.

Every scheduled wake-up replays the whole conversation to the model, so a
"nothing changed" check-in on a long session costs nearly as much as a useful
turn. Ten of them cost real money and caught nothing.

## Bob the Bot — results output architecture (V3)

Applies to the `RESULTS_HY_FY` path only (`deep_results_analysis` and its
callers in `agent.py`). Acquisitions, capital raises, trading updates and the
FYI/Material two-liners are unchanged; the same pattern is intended to extend
to the acquisition and capital-raise memos in a later pass.

### The email is a glance, the Doc is the analysis
A results announcement used to dump a long prose memo into the email. It now
renders a ~360px card: a five-row metric table, a summary of five sentences or
fewer, and two links. The long-form analysis moved to a native Google Doc.

**Why a native Doc, not a PDF or docx**: a Doc reflows on a phone. A PDF does
not. The Doc is created by uploading HTML with
`mimeType: application/vnd.google-apps.document`, which makes Drive convert it
on upload (`create_analysis_doc`). Markdown from the model is rendered to a
small HTML subset first (`_markdown_to_html`: headings, paragraphs, lists,
pipe tables) — enough for what `RESULTS_HYFY_PROMPT` emits, deliberately not a
general markdown engine.

**Drive auth is OAuth, not service account**: a service account has zero Drive
storage quota of its own. Writing into a plain My Drive folder — even one
that's been *shared with* the service account as Editor — returns HTTP 403
"Service Accounts do not have storage quota". This silently killed every Bob
upload for several weeks after the redesign landed: the try/except in `main()`
swallowed the 403, the digest looked fine, and nothing landed in Drive.

`drive_service()` now prefers OAuth2 user credentials (`GDRIVE_CLIENT_ID` +
`GDRIVE_CLIENT_SECRET` + `GDRIVE_REFRESH_TOKEN`) — same pattern Sunday Sally
uses. Authenticated as the human user, files are owned by *them* and use
*their* quota, so plain My Drive folders work. Falls back to service account
with a loud warning only when OAuth secrets aren't set.

Every Drive API call also passes `supportsAllDrives=True`. Without it the
Drive v3 API silently refuses to touch Shared Drive contents; passing it costs
nothing for My Drive writes and future-proofs the code.

**Raw PDF uploads were removed.** The ASX link in the email already points at
the same PDF ASX hosts, so copying it to Drive was pure duplication. Drive is
used only for the analysis Doc now — one file per results item, and that
file is worth opening.

**Drive failures are visible.** When `create_analysis_doc` raises, the results
card renders a red "⚠️ Drive save failed" warning row with the actual error
text, and the failure is stashed on the item's dashboard JSON as `doc_error`.
No more silent Drive.

### The five metrics are locked
Revenue, Underlying NPAT, Underlying EPS, Ordinary dividend, Operating cash
flow — in that order, defined once in `RESULTS_METRIC_ROWS`. Underlying, never
statutory, with the basis labelled. A figure that cannot be found in the source
renders `n/a`; the prompt forbids guessing, inferring or back-solving, because
a wrong number is worse than a missing one now that the number *is* the
product.

Currency comes from the report and is never converted. Non-AUD reporters get an
explicit prefix (`US$4,180m`) so a USD figure can't be read as Australian
dollars; AUD stays a bare `$` because the card's context line already says
"reported in A$". AUD conversion is a later pass.

### One structured LLM call per results item
`deep_results_analysis` makes exactly one Anthropic call returning strict JSON
(`ticker`, `period`, `period_type`, `currency`, `metrics`, `summary`,
`full_analysis`). This matters under `MAX_LLM_CALLS_PER_RUN` during reporting
season, when several portfolio names report on the same morning. The cap is now
env-driven (`MAX_LLM_CALLS`, default 25, set in `daily.yml`) rather than a
hardcoded 15.

**Output-token budget is per-caller.** The first live run of the redesign hit
`parse_error` for both BHP and CSL — `full_analysis` for a large reporter blew
past the shared `max_tokens=4096` and the JSON was truncated mid-string. The
results path now sends its own budget (`CLAUDE_RESULTS_MAX_TOKENS`, default
50000, plumbed through `llm_chat_with_pdfs` / `llm_chat`), while every other
path keeps the smaller `CLAUDE_MAX_TOKENS` default (4096) — a two-liner does
not need a 50k ceiling. When the API reports `stop_reason=max_tokens`,
`_call_anthropic` logs a warning and stashes it on `counters` so the
parse-error path names truncation as the cause instead of the generic
"not valid JSON" — the two need different fixes and shouldn't look identical.

**Long calls must stream, not `.create()`.** The Anthropic Python SDK refuses
non-streaming `messages.create` calls whose expected duration exceeds ~10
minutes — a client-side check to avoid HTTP read-timeouts on long
generations. At Sonnet's output rate, the 50k results budget hits that
threshold, so the first attempt after raising `max_tokens` came back with
"Streaming is required for operations that may take longer than 10 minutes".
`_call_anthropic` now routes any call with `max_tokens >= _STREAMING_MIN_TOKENS`
(8192) through `client.messages.stream`; below that threshold the short
`.create` path stays. The switch itself now lives in `shared/llm.py::send`,
which every agent's Claude calls go through. Streaming keeps the connection alive with periodic
events, so the SDK-side ceiling doesn't apply.

`strawman_post` was left as the existing no-op shim — folding a Strawman draft
into the same JSON would save a call but Strawman output is not currently in
the digest, so there is nothing to save.

### Native PDF in, extracted text as fallback
The results path sends the report (and the deck, if present) as native
Anthropic `document` blocks via `shared/pdf_llm.py`, because table extraction
is exactly where `pypdf` degrades. `extract_pdf_text` remains the *fallback*,
not the default — used when a PDF is missing, malformed, or would push the
request past Claude's 32MB / 100-page whole-request limit. When that fallback
fires, the prompt is told the text came from pypdf so the model prefers `n/a`
over a misread figure.

### Three manual run modes (workflow_dispatch inputs)
`daily.yml` exposes three optional inputs, each mapping to an env var read in
`main()`. Precedence when more than one is set: **RESULTS_TICKER > MANUAL_TICKER
> FORCE_RERUN_TICKERS / normal**.

| Input / env | Window | What it surfaces |
|---|---|---|
| `force_rerun_tickers` | full ASX history | re-runs listed tickers ignoring seen_state; adds non-portfolio names to the portfolio run |
| `manual_ticker` | last 7 days | exclusive; every announcement as FYI plus any results |
| `results_ticker` | last ~6 months (`RESULTS_LOOKBACK_DAYS`, default 180) | exclusive; ONLY the latest HY/FY results, full deep analysis, no FYI noise |

`RESULTS_TICKER` is the "someone at the pub mentioned HPG — what were their last
numbers?" path: a company may have last reported a month or two ago, outside the
24h/7d windows. `most_recent_results_cluster` narrows the 6-month pull to the
single newest reporting event (release + presentation + Appendix 4D/4E within
~14 days of each other) so an old half-year is never bundled with a newer
full-year. No results in the window → a plain "no results found in the last N
days" note, never a blank card.

**Wide-window reruns show the real announcement date on every card.** A
`force_rerun_tickers` run for AHC (2026-10-16) pulled its full ASX history and
surfaced both its CareTech acquisition (announced that morning) and its RTM
acquisition from the same bundle — but a second force-rerun days later, after
AHC had since filed other announcements, made it impossible to tell which
card was which without opening the PDF. Every card builder (`build_results_block`,
`build_fundraise_block`, `build_trading_update_block`, `build_4c_block`,
`build_acquisition_block`, `build_remuneration_block`, `build_high_impact_block`)
takes an optional `announced` string, rendered as one muted line under the
card header (`_announced_html_line` / `_announced_text_line`) and, where there
is no card (a plain MATERIAL two-liner, an FYI headline), inline as
`Announced: <date>`. `main()` computes `wide_window_tickers =
results_tickers | manual_tickers | force_rerun_tickers` once and sets
`show_date = ticker in wide_window_tickers` per ticker; `announced` is the
announcement's own `date` field (from `asx_fetch.py`, already on every item)
when `show_date`, else `""` — so the normal daily run (`HOURS_BACK`, no
override) never shows it, because "today" already answers the question
there. It is never derived from `_status`, "when the LLM ran", or anything
else — it is always the ASX-reported date of that specific document.

**One-off modes never touch shared state.** When `RESULTS_TICKER` or
`MANUAL_TICKER` is set, `main()` emails the analysis but skips both the
`bob.json` write and the seen_state save. Two reasons: a single ad-hoc ticker
must not clobber the portfolio dashboard, and — because the bob.json write
stamps `last_run = today` — a morning phone query would otherwise trip the
evening scheduled digest's catch-up guard (`_already_sent_today`) and stand the
real digest down. An ad-hoc query must never cost that night's portfolio digest.
This matches the log line manual mode always claimed ("one-off, not saved to
state") but the code previously contradicted.

### Results detection is pattern-based, not a phrase list
`looks_like_results_title` gates the entire results path: no match, no
`deep_results_analysis`, no card, no PDF. It used to be a list of literal
phrases (`"full year results"`, `"results presentation"`, …), which silently
lost Brambles' FY26 report on 2026-08-20 — BXB styles its headlines
"2026 Full-Year Result **presentation**" (singular "Result"), "Full Year
Statutory Accounts" and "2026 Full-Year ASX & Media Release". All five BXB
documents downloaded, none was recognised, and the digest showed BXB only
under MATERIAL/FYI while MVP the same morning analysed fine. Nothing in the
run looked like an error, which is what made it expensive to spot.

It is now a regex list: a reporting period (`half`/`full year`, `FY26`,
`1H FY2026`, `interim`, `annual`) beside a results-document noun (`result(s)`,
`report`, `accounts`, `release`, `presentation`), plus standalone hard yeses
(Appendix 4D/4E, `preliminary final report`, `statutory accounts`). Loosening
`results` to match the singular means AGM **voting** results now need an
explicit hard-no, alongside the existing transcript/webcast exclusions.
Real headlines from that morning are pinned as tests in
`tests/test_agent_gate_and_rerun.py` — both the ones that must match and the
governance statement / dividend notice / substantial-holding notice that
must not.

### JSON repair recovers content, it never invents it
`_parse_analysis_json` tries four things, cheapest first: a straight parse, the
outermost `{...}` span (ignoring prose either side), that span with string
bodies sanitised, and finally unclosed brackets closed.

The sanitising step exists because `full_analysis` is a multi-thousand-character
markdown blob inside one JSON string, and one slip in a long generation fails
the whole item — a raw newline instead of `\n`, or a markdown escape like `\%`
that JSON rejects. SPZ died this way on 2026-08-19 with the generic
"not valid JSON". Re-encoding those characters loses nothing the model wrote.

Bracket-closing is different and is deliberately fenced off: it only runs when
the API did **not** report `stop_reason=max_tokens`. Balancing brackets on a
truncated response yields an object whose `full_analysis` stops mid-sentence,
which would render as a clean card — the one outcome this design forbids.
Truncation stays a `parse_error` that names the cap. In practice a truncated
response ends inside an unterminated string, so there is nothing to close
anyway; the guard is there so a future change can't quietly turn truncation
into a plausible-looking result.

### Capital & debt raises render as a card, not a blob
A capital raise or debt raise (`CAPITAL_OR_DEBT_RAISE`) used to dump the whole
LLM memo into the email as one wall of text. It now uses the same phone-first
card as results and remuneration: a header **verdict pill** that answers "is
this a rescue?" (OPPORTUNISTIC green / NEUTRAL blue / DEFENSIVE amber / RESCUE
red), a locked six-row quick-take (`FUNDRAISE_QUICK_TAKE_ROWS`: Type, Amount,
Structure, Use of funds, Cost/dilution, Leverage), a <=5-sentence summary, and
the forensic detail — tranche table, maturity-ladder discussion, interest-rate
positioning, balance-sheet walk — in the attached PDF. `deep_capital_memo`
returns structured JSON `_status`-tagged exactly like `deep_results_analysis`
(streaming at `FUNDRAISE_MAX_TOKENS`, raw text preserved on a parse failure);
`build_fundraise_block` / `build_fundraise_doc_html` render it; the dashboard
card (`_CAPITAL_FIELDS`) shows verdict + kind + quick-take + summary.

**It never invents a balance-sheet figure from the announcement.** A raise
announcement rarely restates the prior maturity ladder, current net debt, or
gearing before/after. The prompt (`FUNDRAISE_PROMPT`) is hard-gated: use only
what the announcement discloses, and where a figure is absent, write "not
disclosed in this announcement" and list it as a key question — never estimate
it. Same rule as the locked results metrics.

**The prior leverage baseline comes from EODHD, clearly labelled.**
`fetch_debt_profile(ticker)` pulls the company's latest reported balance sheet
(`shared/eodhd.py::debt_profile` — gross/net debt, cash, equity, EBITDA, Net
Debt/EBITDA, gearing, as-of date) and it feeds three places: the card gets one
extra "Prior balance sheet" row, the PDF a labelled table ("the leverage
baseline *before* this raise, not a figure from the announcement"), and the LLM
call gets the figures as context so the before->after in `full_analysis` is
grounded in real prior numbers (if new debt, leverage rises by the raised
amount; if refinancing, roughly neutral). This is the one place Bob reads market
data — strictly best-effort (`EODHD_API_TOKEN` in `daily.yml`, added to the
`test_eodhd_only.py` workflow list): if EODHD is unconfigured, uncovered, or
fails, the card renders exactly as before. EODHD figures never leak into the
`quick_take` (which is announcement-only); they are a separate, sourced block.

### Acquisitions render as a card, not a blob
(V3.2) AHC announced two acquisitions the same morning (2026-10-16) —
CareTech Systems and RTM Hold Co — and both rendered as back-to-back walls
of unstructured prose under "Acquisition (analysed via PDF)". Same fix as
fundraise/trading-update/4C: `build_acquisition_block` is a locked 5-row
quick-take (Target, Consideration, Multiple, Funding, Strategic fit), a
<=5-sentence summary, and the forensic detail (deal summary, what they
bought net of anything that evaporates on consolidation, integration risk,
balance sheet impact, red flags, bull/bear/key questions) in the attached
PDF (`build_acquisition_doc_html`). `deep_acquisition_memo` is the one
structured call, `_status`-tagged exactly like the others, streaming at
`ACQUISITION_MAX_TOKENS` (default 50000, same as results/fundraise — a
two-target deal can run just as long as a single reporter).

No verdict pill on this card, unlike fundraise (opportunistic/rescue) or
trading updates (beat/miss): there isn't a single good/bad axis for an
acquisition the way there is for a raise or a guidance update, so the
quick-take rows plus the full forensic PDF carry the judgement instead —
same choice as the results card, which also has none. No `has_data` gate
either: an acquisition announcement IS the acquisition, not a pre-notice
that one is coming, so the notification-only failure mode that motivated
the gate on trading updates and 4C doesn't apply here.

### Trading updates and 4C/5B quarterly reports render as a card, not a blob
(V3.1) The same "card, not a blob" rework as capital raises, now applied to
the two other high-frequency announcement types that used to dump a wall of
text into the email. DRO's real FY2026 committed-revenue update rendered as
seven unstructured paragraphs under "Trading Update / Guidance (analysed via
PDF)" on 2026-10-15 — correct content, unreadable shape. It now gets
`build_trading_update_block`: a locked four-row quick-take (headline number,
vs guidance, driver, balance sheet) behind a verdict pill
(UPGRADE/DOWNGRADE/WITHDRAWN/IN LINE/REVIEW), a <=5-sentence summary, and the
same forensic markdown as before in an attached PDF
(`build_trading_update_doc_html`). `deep_trading_update_memo` is the one
structured call, `_status`-tagged exactly like `deep_results_analysis` /
`deep_capital_memo`.

**Appendix 4C / 5B is a different document shape, not a flavour of trading
update.** MVP's real Appendix 4C that same morning was classified by the same
"quarterly" keyword as a bare revenue/guidance release and got the identical
wall-of-text treatment — despite containing the one number a small-cap holder
actually wants: Question 8, "estimated quarters of funding available".
`classify_from_title_only` now checks `appendix 4c` / `appendix 5b` /
`quarterly cash(.)?flow` *before* the generic trading-update keywords and
returns `QUARTERLY_4C`, its own bucket with its own template
(`deep_4c_memo` / `build_4c_block` / `build_4c_doc_html`): a three-row
operating/investing/financing cash-flow table (this quarter + YTD where the
form has a YTD column), the cash position, and the runway figure as the
header verdict pill (URGENT <2 quarters / WATCH <4 / ADEQUATE <8 / LONG
RUNWAY >=8 / SELF-FUNDED when operating cash flow was positive and Item 8
was correctly left blank). The prompt tells the model to use the company's
own reported Item 8.7 when present, and to compute the ratio itself
(cash ÷ net operating+investing outflow) when operating cash flow is negative
but Item 8 was left off the form — never to leave a cash-burning company
without some runway number.

**A notification that a report is coming is not the report.** MSV's actual
announcement that morning was an administrative notice — "the FY27 Q1
quarterly update will be released on 19 October 2026, with a webinar to
follow" — no financial content at all. Two independent bugs let it through:
its title, "FY27 Q1 results briefing", matched the generic
`\bresults?\s+(?:...|briefing|...)\b` pattern in `looks_like_results_title`
(a quarter-only "results" title is never a full HY/FY statement — ASX names
report HY/FY under Appendix 4D/4E — so `_RESULTS_TITLE_HARD_NO_PATTERNS` now
excludes Q1/Q2/Q3 titles, deliberately leaving Q4 alone since some reporters'
Q4 doubles as the full-year result); and even with that fixed, nothing
stopped a genuinely content-free trading-update or 4C document from running
the real template and rendering a card of nothing but "n/a" — which is
exactly what happened. `deep_trading_update_memo` and `deep_4c_memo` both ask
the model to set `"has_data": false` and a one-line `summary` (plus
`notice_date` if one is given) when the document is purely a "coming soon"
notice; the main loop checks that flag before building any card or PDF and,
if false, does nothing beyond the FYI line every announcement already gets —
no wasted analysis, no misleading table. Critically, every *other* outcome
(`skipped`, `failed`, `parse_error`, `no_content`) forces `has_data: True` in
code, never leaving it to the model — a half-broken digest must never look
like a quiet non-event, so only a successfully parsed `"ok"` response that
the model itself marked `has_data: false` can suppress a card.

*Open question, not yet built*: whether a detected "report coming on
`notice_date`" should write a calendar reminder. Feasible — Bob's Drive OAuth
pattern (`shared/gdrive.py`) extends the same way to a Calendar scope — but
deliberately not wired up here; ask if you want it.

### Four distinct outcomes, none of which can look clean
`deep_results_analysis` tags its return with `_status`:

| `_status` | Cause | Email block shows |
|---|---|---|
| `ok` | JSON parsed | the normal card |
| `skipped` | `MAX_LLM_CALLS_PER_RUN` reached | `Analysis skipped: run-call cap reached` (not an error) |
| `failed` | Anthropic API exception | `ANALYSIS FAILED` badge + the real error class/status |
| `parse_error` | model replied, but not valid JSON | `ANALYSIS FAILED` badge; raw text preserved in the Doc |
| `no_content` | no usable PDF or text; no LLM call made | "open manually" |

The rule: a half-broken digest must never look like a clean one. A parse
failure never falls back to a plausible-looking placeholder — the raw model
output goes to the Doc verbatim under a "Raw model output (unparseable)"
heading so nothing is lost.

### Email HTML constraints (do not "modernise" this)
The results card is table-based with inline styles only, and there is a test
asserting no `display:flex`, `display:grid`, `<style>` or `class=` appears in
it. Email clients strip `<style>` blocks and mishandle flexbox/grid; a
two-column `<table>` (label `<td>` + value `<td>`) is the only reliable way to
get label-left / value-right rows. Change values are coloured with an inline
`style="color:…"` span — green up, red down, muted grey for `n/a` / `n/m`.

Digest blocks may now be either a plain string (escaped, pre-wrap) or a
`{"text": ..., "html": ...}` dict for blocks that build their own email-safe
HTML (`_block_text` / `_block_html` in `agent.py`).

## Singapore Slinger — Singapore Exchange announcements (V4)

The SGX bot is Singapore Slinger — "slings information" from SGX. It's a
distinct persona from ASX Bob (their JSON shapes overlap by design, but
the two are independent bots on the dashboard now, not "Bob with a
regional badge"). The display name changed; the underlying `sgx_*`
module and `BOB_SG_*` constant names stayed to avoid a churny rename
across every import.

Round 1 landed the fetch (`sgx_fetch.py`). Round 2 added the full daily
digest: classifier + PDF fetcher + LLM analysis (results only) + email,
all wired into `sgx_daily.yml` with a morning SGT cron. Round 3 wires
the dashboard: Slinger writes `docs/data/slinger.json` after each real
run, the sgx_daily workflow commits + pushes it, and
`.github/workflows/theo-pages.yml` picks up the `Singapore Slinger Daily`
`workflow_run` completion event and republishes the site.

Layout — five top-level `sgx_*` modules keep the SGX path a clean
horizontal split from `agent.py` (which stays ASX-only, untouched):

| File | Role |
|---|---|
| `sgx_fetch.py` | Playwright prime + REST replay (Round 1) |
| `sgx_classify.py` | Category-code -> bucket (RESULTS_HY_FY / DIVIDEND / SHARE_BUYBACK / ACQUISITION / …), title-regex fallback |
| `sgx_pdf.py` | `links.sgx.com` URL -> local PDF(s). Handles both direct-PDF and HTML-landing-page cases |
| `sgx_email.py` | Digest HTML/text builder — same table-only inline-styles shape as `agent.py`, `S$` prefix, "SGX" badge in header, full markdown analysis rendered inline in the results card |
| `sgx_agent.py` | Orchestrator: fetch → classify → PDF → LLM (for results) → email with PDFs attached → seen-state → dashboard JSON |

**No coupling to `agent.py`.** `import agent` drags in `weasyprint`,
`pypdf`, `bs4`, and other deps the SGX box doesn't need for anything else,
and any change to `agent.py` becomes an SGX regression risk. The Anthropic
streaming plumbing and SMTP send that used to be duplicated here now come
from `shared/llm.py` and `shared/email_service.py` (stdlib-only at import
time), not from `agent.py`.

**No Google Drive on the SGX path.** ASX Bob writes a native Google Doc
per results item; SGX Bob deliberately doesn't.

The email body carries the metric card, the short summary, and clickable
**links** to the source PDFs on SGX (rendered from the `source_url` on
each `FetchedPdf` — see `sgx_pdf.py`). The deep analysis (`full_analysis`
markdown) does NOT render in the email body; it goes into a standalone
**PDF attached** to the email so the user can forward one file to
friends. This split is intentional:

- Source PDFs → **linked** (not attached) so the email stays lightweight
  and Gmail doesn't warn about size; the originals live on SGX anyway.
- Analysis PDF → **attached** so it forwards cleanly as a self-contained
  file rather than an inline HTML block that reflows when re-emailed.

The analysis PDF is rendered by `_render_analysis_pdf` in `sgx_agent.py`
via Playwright + installed Chrome (`channel='chrome'`, headless,
`page.pdf()`). Chrome is already provisioned on the self-hosted Windows
runner for `sgx_fetch`'s token-prime step, so this adds no dependencies.
The HTML for that PDF is built by `build_analysis_pdf_html` in
`sgx_email.py` — a complete `<!doctype html>` document with an `@page A4`
rule, the same metric table as the email card, the summary, and the full
markdown analysis. Attachment total is capped at 20MB but the analysis
PDFs are ~50-200KB each, so the cap is really just a safety net.

The PDF is a **standalone report the user forwards to peers**, so its
layout matters more than the email card's:

- Cover header with big ticker + issuer + period pill + generated-on
  timestamp + currency line, on the deep-green SGX bar.
- Metric table: bordered rows, YoY colour-coded (green +ve / red -ve /
  muted grey n/a), basis label under each figure.
- Summary rendered as a bordered callout ("verdict first") -- the
  five-sentence line the prompt asks for.
- Deep analysis rendered through `_markdown_to_email_html(pdf_mode=True)`
  which bumps sizing, adds accent-underline section headers on `##`,
  page-break-inside:avoid on tables + blockquotes, and supports `> ...`
  blockquotes as bordered callouts (a way for the LLM to flag one
  must-not-miss sentence).
- Chrome print-CSS `@page @bottom-right` footer gives page X of Y
  numbers; a disclaimer + "verify on links.sgx.com" line closes the
  document.

The user prompt to Claude is structured deliberately: **hint FIRST**
(so the model reads context before schema boilerplate), then a
Slinger-specific block noting SGX holding-company patterns, quality
expectations (audience: sophisticated peers, target 800-1500 words of
real numbers), and currency-prefix rules (S$/US$/Rp — never bare `$`).
Ordering matters -- an earlier version appended the hint at the end
and the C07 (JC&C) analysis came back generic-P&L-shaped, ignoring
the Astra hint entirely.

**Metric JSON keys are load-bearing.** `sgx_email._results_card_html`
reads `dividend_ordinary` (not `ordinary_dividend`) and `change_pct`
(not `change`) — those are the keys the `RESULTS_HYFY_PROMPT` schema
tells the model to emit. Earlier code used the wrong names and the
first live SGX results email came back with a blank YoY column and
`n/a` in the dividend row despite the model returning real numbers.
`tests/test_sgx_email.py::TestResultsCard::test_card_shows_yoy_change_column`
and `test_card_renders_dividend_row` pin the correct schema.

**SGX classification is metadata-driven, not title-regex.** Every SGX
row carries `sub` (e.g. `ANNC17`), `cat` (e.g. `ANNC`), and
`category_name` (e.g. "Financial Statements and Related"). We map those
directly to Bob's buckets. Title regex is fallback only for the
`ANNC18` General Announcement bucket. This is much cleaner than ASX's
title regex (which lost BXB's FY26 release before being rewritten) — SGX
gives us structured signal for free.

**Seen-state file: `state_seen_sgx.json`.** Separate from ASX's
`state_seen.json` — different exchange, different retention window,
independent lifecycle. `sgx_daily.yml` restores/saves it via
`actions/cache`, same pattern `daily.yml` uses for ASX.

**Cron: `15 0 * * *` UTC = 08:15 SGT.** ~1h15m after SGX opens, long
enough for the ~7am pre-open batch to have landed.

Round 1 was fetch-only: `sgx_fetch.py` pulled the announcements list
for every ticker in `tickers.yaml`'s `sgx:` section and wrote JSON to
`outputs/sgx/announcements.json`. Round 2 keeps that path (via the
`fetch_only=true` workflow dispatch input) as a diagnostic mode.

### Why SGX must run on the self-hosted Windows runner
Two independent SGX-side filters, both discovered during the spike
sequence (#158 → #166):

1. **TLS fingerprint filter.** `api.sgx.com` returns 403 to raw
   `requests` calls (and to GitHub-hosted ubuntu runner IPs, even from
   headless Chromium). Only a browser session that matches installed
   Google Chrome gets through.
2. **Signed `authorizationtoken` header.** `investors.sgx.com` is a
   Flutter Web app that computes a ~130-char signed token client-side
   and injects it on each `api.sgx.com` request. Without it, the
   announcements list endpoint returns 401 even when everything else
   about the request is right. There is no way to reproduce this token
   from Python alone — it has to be captured from a live browser.

`sgx_fetch.py` handles both by launching Playwright with
`channel='chrome'` (installed Chrome, not bundled Chromium) and a real
Chrome User-Agent (Playwright otherwise stamps `HeadlessChrome`), then
navigating to the announcements page and intercepting the first
`api.sgx.com` request that carries a non-empty `authorizationtoken`.

**The token is not ticker-bound** (verified in #165), so one Playwright
prime does the whole portfolio — subsequent REST calls use
`context.request` with the captured token forwarded as a header.

### The URL shape that returns real data
Getting the query params right was itself a diagnostic round (#166 vs.
the earlier zero-item response). The endpoint Flutter actually fires:

```
GET /announcements/v1.1/securitycode
    ?value=D05&securityCodeParams=D05
    &pagestart=0&pagesize=25
    &periodstart=YYYYMMDD_HHMMSS&periodend=YYYYMMDD_HHMMSS
    &exactsearch=true
```

Both `value` and `securityCodeParams` must echo the ticker (not the
literal string `"securitycode"`). No `cat=` or `sub=` filters — those
narrow the result set and return zero for a full company view. Both
period bounds are compact SGT timestamps. All of that is encoded in
`_list_url` and pinned by `tests/test_sgx_fetch.py::test_matches_flutter_shape`.

### Row shape
Each returned announcement dict carries the ASX-compatible core keys
(`exchange`, `ticker`, `date`, `time`, `title`, `url`) so future
downstream code doesn't need to branch on exchange, plus the SGX-native
extras (`ref_id`, `id`, `sub`, `cat`, `category_name`, `issuer_name`,
`submission_ts_ms`) that the eventual SGX classifier will key off.

SGX classifies natively via `category_name` and `sub` codes (e.g.
`ANNC13`=Share Buy Back, `ANNC15`=Employee Stock Option, `ANNC17`=
Financial Statements, `ANNC18`=General Announcement) — much cleaner
signal than ASX's title regex when Round 2 lands.

### Workflow
`.github/workflows/sgx_daily.yml` (workflow name: **Singapore Slinger
Daily**) — manual dispatch AND daily cron (`15 0 * * *` UTC). Runs on
`[self-hosted, Windows]` using the PowerShell + machine-Python pattern
from `ned_transcript.yml`. Reads `state_seen_sgx.json` via
`actions/cache` for dedup across runs, runs `sgx_agent.py`, emails the

site republishes. Dispatch inputs: `tickers` (override the yaml

mode — just dump JSON, no LLM/email), `results_ticker` (pull LAST HY/FY
report + deep analysis), and `results_hint` (free-form context appended
to every LLM call — use it when the report doesn't make the shape of
the business obvious, e.g. "Haw Par's main asset is its UOB stake, not
Tiger Balm trading").

### Dashboard integration
Slinger writes `docs/data/slinger.json` (same shape as `bob.json`:
`last_run` + `high_impact` / `material` / `fyi` arrays) after each
non-dry-run. Written on both portfolio and results-ticker modes — a
one-off `results_ticker` query does show up on the site until the next
scheduled portfolio run overwrites it. This is a deliberate departure
from ASX Bob's "one-off never touches the dashboard" rule; Bob has a
catch-up cron the dashboard write would trip (see the `_already_sent_today`
guard in `agent.py`), Slinger doesn't.

`scripts/build_dashboard.py` renders `_slinger_section` (defined in
`dashboard/sections/slinger.py`) between Bob's card and Wally's. High-impact items reuse Bob's `_render_analysis_sections`
because the metrics JSON schema (`dividend_ordinary` + `change_pct`) is
identical, and Slinger's card adds a **Source PDFs** link list (SGX
hosts them, so the dashboard just links back). Material/FYI items only
carry `ticker` + `title` + `url`, so they render as compact rows.

**Last-two-runs history.** `_update_slinger_history` keeps
`docs/data/slinger_history.json` — the two newest distinct runs,
newest first — mirroring Bob's `bob_history.json`. `_slinger_section`
renders the current run open and the previous one collapsed in a
`<details>` block. The sgx_daily workflow's dashboard-commit step
`git add`s `slinger_history.json` alongside `slinger.json` and the
rebuilt `index.html`. Deduping is signature-based so a rebuild
triggered by another agent (Theo/Bob/Ned) with no new Slinger data
doesn't churn the file.

**PowerShell + Unicode gotcha (do not "modernise" the commit
message).** The Slinger dashboard-commit step runs in PowerShell on
the self-hosted Windows runner, which reads workflow scripts as
cp1252. A bare em dash `—` in a commit message like `"Dashboard update
— Slinger [skip ci]"` breaks the parser mid-file with `The string is
missing the terminator: "`, kills the commit + push, and the site
never picks up Slinger's data even though the run's other steps
succeeded (email sent, `slinger.json` written to disk, then thrown
away when the runner cleans up). Keep the step's git commit messages
ASCII-only — the fix that got LCC's second run to publish uses `--`,
not em dash.

The same em dash killed Ned's YouTube publish on 2026-09-23
(`ned_transcript.yml`, "Dashboard update — Ned transcripts"): the transcript
was fetched and emailed, then the commit step died and nothing reached the
site. `tests/test_hindsight.py::test_powershell_workflows_are_ascii_only` now
fails if any `shell: powershell` workflow contains a non-ASCII character.

**Python stdout on Windows is cp1252 too.** Same shape, different
place: a `print(f"... → ...")` in `scripts/build_dashboard.py` crashes
with `UnicodeEncodeError: 'charmap' codec can't encode character
'\\u2192'` when the dashboard is rebuilt on the Windows runner (Bob's
ubuntu never sees this). Killed the C07 rerun mid-way through
`build_dashboard.py` -- `slinger.json` had already been committed but
`index.html` never got rebuilt with the Slinger card. `build_dashboard.py`
now calls `sys.stdout.reconfigure(encoding="utf-8")` at import time,
so any non-ASCII char in a print / log line stops being a load-bearing
bug. Same fix belongs anywhere else that runs on the Windows runner
and prints unicode.

**Python `read_text()` on Windows is cp1252 too — same platform, same
gotcha, different failure mode.** Python 3.14's `Path.read_text()`
defaults to `locale.getpreferredencoding(False)`, which is cp1252 on
the Windows runner. When `build_dashboard.py` reads a `slinger.json`
whose Windows-side sgx_agent write correctly used
`encoding='utf-8'`, the on-disk bytes `0xC2 0xA2` (UTF-8 for `¢`) get
decoded as cp1252 to two characters `Â¢`. `_update_slinger_history`
then writes that mojibake back to `slinger_history.json` as
`"\\u00c2\\u00a2"`. On the ubuntu Publish site runner the default is
UTF-8 so the same file reads correctly and gets rewritten as
`"\\u00a2"` — so every Publish site run tries to "fix" the mojibake,
produces a working-tree diff on `slinger_history.json`, and if that
file isn't in the `git add` list the follow-up `git pull --rebase`
bails with **"cannot pull with rebase: You have unstaged changes"**
and takes the whole publish down. That's what left the D05 run's
Slinger card unpublished. Fixes:
1. `_load(name)` in `build_dashboard.py` reads as UTF-8 explicitly.
2. `slinger_history.json` is in the theo-pages `git add` list so
   platform-cycle diffs get committed rather than blocking the rebase.
Regression pinned in
`tests/test_build_dashboard_slinger.py::test_load_reads_utf8_regardless_of_locale`.

**JSON parser: `_parse_analysis_json` in `sgx_agent.py`** progresses
through four fallbacks, cheapest first, each preserving content
exactly:

1. Straight parse after stripping code fences.
2. Outermost `{...}` span, ignoring prose either side.
3. That span with string bodies sanitised (raw newlines re-encoded as
   `\\n`, invalid escapes like `\\%` dropped) — Bob's SPZ failure mode.
4. **Carve `full_analysis` out as raw text** and re-parse the header —
   the C07 failure mode. The model wrote `"impairment of X, Y and Z."`
   inside the `full_analysis` string with unescaped inner quotes, so
   `json.loads` bailed on the whole object. Extracting the markdown
   body separately means quotes / backslashes / anything inside
   `full_analysis` never has to be JSON-escaped. Header JSON (small,
   well-behaved metrics + summary) parses fine on its own, then the
   raw markdown gets reattached. Regressions pinned in
   `tests/test_sgx_parse.py`.

No bracket-closing fallback — a truncated response stays a
`parse_error` so a half-broken digest never renders like a clean one
(same rule Bob's ASX path enforces).

The Publish site workflow (`theo-pages.yml`) has `Singapore Slinger
Daily` in its `workflow_run` triggers so a Slinger run completing kicks
off a Pages redeploy — same pattern Bob/Ned/Wally/Sally use. Note the
Pages workflow fires on completion regardless of the triggering run's
conclusion (deliberate — a run that emailed then tripped on a later
step has still committed data worth publishing), so a red Slinger
whose commit step failed will still trigger a redeploy — it just
deploys the pre-Slinger state.

## Wally the Watcher — target ("buy") prices

Wally flags a ticker on two independent triggers now, not one:
`flagged = near_low or below_target`. `near_low` is the original within-5%-of-
52-week-low screen; `below_target` fires when the current price is at or below a
per-ticker target price. Below-target tickers get exactly the same downstream
treatment as near-low ones (range + value charts, email detail, dashboard row),
because everything keys off `row.flagged` — the only change in `wally/main.py`
is passing `target_price=wl.target_prices.get(ticker)` into `screen_snapshot`.

Target prices live in the watchlist YAML, loaded by `wally/watchlist_loader.py`
into `Watchlist.target_prices` (`dict[str, float]`, empty by default so plain
string lists behave exactly as before). Three accepted forms, mixable in one
file: a per-entry mapping with `target_price:` (or the `buy_price:` alias the
TII list uses), or a top-level `targets: { TICKER: price }` block. Keys are
`.strip().upper()`-normalised; prices are coerced to float and anything `<= 0`
or non-numeric is dropped. GBX pence buy prices are written the way the source
spreadsheet holds them — `"500.00p"`, `"9,500.00p"` — and `_coerce_price`
strips the thousands comma and trailing `p` to a numeric pence value; so
`watchlists/tii_watchlist.yaml` carries AUTO/LSEG/RMV buy prices in pence.
Whatever unit a buy price is in, the quote Wally screens it against must match:
UK names are quoted in pence on their home exchange, so a pence buy price
compares correctly there.

There are five standard watchlists, de-duplicated in priority order
**Income → JM → Aussie Tech → Cornerstone → Nap Taker**: a ticker that appears
in more than one is kept only in the highest-priority list. **Buy prices follow
the ticker**, not the list — a global price map (Cornerstone's Buy-Below
preferred, else Nap Taker's) is attached to whichever list each ticker lands in,
so a name that moves lists still carries its buy price and stays flagged.

The lists and where their names/prices come from:

- **Income Watchlist** (`income_watchlist.yaml`) — the best dividend payers
  pulled out of every other list (except TII75): names with a ~4%+ cash yield
  plus the franked blue-chip anchors (big-four banks, BHP, Telstra, Transurban,
  the income REITs). Yield traps (GQG, ADH, IPH — high yield only because the
  price collapsed) and broken theses (LAU) are deliberately excluded. Highest
  priority, so these names live here rather than in JM/Cornerstone/Nap Taker.

- **JM Watch List** (`jm_watchlist.yaml`) and **Aussie Tech Watchlist**
  (`aussie_tech_watchlist.yaml`) — the user's own ticker lists (from
  `Watchlists_Aug_26`), no native buy prices; they inherit prices via the map.
- **Cornerstone Watchlist** (`tii_watchlist.yaml`) — the list formerly named
  "TII Watchlist", renamed so the source's buy prices aren't published under
  their brand. Filename kept as `tii_watchlist.yaml`; the display `name:` is
  "Cornerstone Watchlist" and `_load_portfolio_targets` maps that name to
  `config/tii_portfolio_targets.yaml`. Buy prices from the TII sheet's
  "Buy Below" column, GBX pence as written.
- **Nap Taker Investing** (`naptaker_watchlist.yaml`) — analyst buy
  recommendations under two years old, merged from the five Motley Fool
  scorecard tabs (Buy status only), deliberately not named after the source.
  Buy price = the price at the date of recommendation. US names are stored bare
  (no `.AX`); a few source tickers needed correcting off the intact concatenated
  name column (e.g. AMD, GOAT, SGLLV, HWM, TTD).

`tii75_watchlist.yaml` is a separate canonical list and stays untouched at
exactly 30. `config/tii_portfolio_targets.yaml` (`buy_below`, used for the
email's Portfolio Targets block) is a separate, older source and may lag.

`TickerScreenResult` gained `near_low`, `target_price`, `below_target` and
`distance_to_target_pct` (all defaulted, so the empty/error constructors in
`main.py` still work). They flow into `outputs/` JSON via `to_dict()`, into
`docs/data/wally.json`, and onto the dashboard as a **Buy Price** column plus a
**Trigger** cell (below-buy hits highlighted green as a buying opportunity). The
email flagged table gained matching **Target** and **Trigger** columns
(`_flagged_row` / `_trigger_reasons` in `wally/email_report.py`).

### Multi-year lows and 52-week ranges
A name near its 52-week low is also checked against its **2/3/5/10-year
lows** (`WALLY_MULTI_YEAR_HORIZONS`, same `WALLY_LOW_THRESHOLD_PCT` band;
2 years = 104 weeks). `multi_year_low` in `wally/screening.py` returns the
longest horizon the price is within the band of, and only counts a horizon
the history actually reaches (a stock listed 18 months ago has no 2-year
low). A 2-year low inside the band implies a 52-week low inside it, so only
near-low names fetch the 10-year history: one extra EODHD call each
(`fetch_long_closes`). Closes are split-adjusted only
(`split_adjusted_closes`): EODHD's `adjusted_close` also strips dividends,
which drags old prices down and hides a genuine multi-year low. Multi-year
lows sort first and show as `3Y LOW` in the email, on the site and in the
trigger ("3y low"). It is a stronger label on an existing flag, not a new
reason to flag.

Every flagged name also gets `shared.ranges` 52-week P/E and P/FCF
(statutory TTM, same as Sally): range bars in the email table, `ranges_52w`
in `wally.json`. The dashboard shows a 52-week price-range slider per row
(green near the low, red near the high, green tick at the buy price).

### Wally's Shortlist — the weekly "best opportunities" pass

The flagged tables are a tripwire (near a 52-week low, or below a per-ticker buy
price), not a verdict: buy prices go stale, and "cheaper than its own history"
can still be absolutely expensive (80x falling to 60x is still dear). So the
combined run adds a valuation-aware shortlist at the top of the email and the
dashboard card. Lives in `wally/shortlist.py`; wired only into
`_process_watchlists_combined` (the Friday `--all-combined` run), TII75 excluded.

Two stages:
1. `_opportunity_score` — deterministic, valuation-first, over **every** screened
   row (so a genuinely cheap name that isn't flagged can still surface). Rewards
   low forward PE, high FCF yield, low EV/EBITDA, income; de-rating and
   buy-price proximity are tie-breakers only. A hard gate caps the score for any
   name at/above `WALLY_SHORTLIST_EXPENSIVE_PE` (default 40) — the "60x is still
   60x" rule. This means the combined run now fetches a valuation snapshot for
   every ticker (not just flagged ones); best-effort, failures degrade to a
   de-rating-only score.
2. `_rank_with_llm` — one Claude call (`claude-opus-4-6`, adaptive thinking) over
   the top `WALLY_SHORTLIST_CANDIDATES` (default 12). Returns up to
   `WALLY_SHORTLIST_PICKS` (default 5) ranked picks with thesis / why-now / risk,
   and is explicitly allowed to return fewer — even zero ("sitting on hands") —
   rather than pad the list.

Never fatal: no API key → `skipped`, LLM/parse failure → `failed`, and Wally
reports exactly as before. The shortlist is written to `docs/data/wally.json`
under a top-level `shortlist` key and rendered by `dashboard/sections/wally.py`
(`_shortlist_block`) at the top of the card; the email block
(`render_email_html`) is table-only inline styles like every other Wally email.
Injected `fetch_valuation` / `llm_send` / `make_client` keep it testable offline
(`tests/test_wally_shortlist.py`).

### Watchlists live in `watchlists/`, and only there
`wally/config.py` used to point `STANDARD_WATCHLISTS` at `.github/Watchlist/`,
a second copy dating from March 2026. Every improvement — the Aug-26 buy-price
sync, the TII → JM → Aussie Tech de-duplication — was written to
`watchlists/`, which nothing loaded. Wally screened the old 74-name TII list,
returned `target_price: null` on every row, and the below-target trigger was
dead for as long as it existed, while the run reported success and the email
looked normal. `.github/Watchlist/` has been deleted so there is one place to
edit, and `tests/test_wally_watchlist_paths.py` fails if a second copy
reappears or if the TII list stops carrying prices.

## Shorty — ASIC short-interest report

Weekly numbers report, not an event-driven digest: ASIC's aggregate short
position data moves slowly day to day, so Shorty emails the same table every
Monday regardless of whether anything changed (same pattern as Wally's
weekly screen) rather than trying to detect "what's new". No LLM call, no
PDF, no seen-state — the whole pipeline is a CSV fetch, a lookup and a diff.

**Data source, confirmed against a real file, not guessed.** ASIC publishes
one aggregate short-position CSV per ASX trading day at
`https://download.asic.gov.au/short-selling/RR{YYYYMMDD}-001-SSDailyAggShortPos.csv`,
columns `Product`, `Product Code`, `Reported Short Positions`,
`Total Product in Issue`, `% of Total Product in Issue Reported as Short
Positions` — all confirmed from the live 12-Oct-2026 report before writing
any fetch code (`shorty_fetch.py::EXPECTED_HEADERS`). A header shape that no
longer matches raises `AsicFetchError` rather than silently mis-mapping
columns. There is no index of available dates to query, and reports never
exist for weekends, public holidays, or before ASIC's publication lag
catches up — so "the most recent report" and "the report closest to 1 July"
are both found by probing candidate dates with plain GETs, not by assuming
today's date works.

**`find_most_recent_report`** walks backward only from today, stopping at
the first date that resolves — it must never probe a future date, because
today's or yesterday's report routinely doesn't exist yet.
**`find_nearest_report`** (used for the FY-start baseline) walks outward in
both directions from the target date (0, +1, -1, +2, -2, ...) so the
genuinely closest available report wins regardless of which side of 1 July
it falls on. Neither function has a cap worth skipping past in production —
`find_most_recent_report` gives up after 20 days back, `find_nearest_report`
after 14 days either side — and both log a plain-text reason when they do.

**A missing figure renders as "not reported", never 0%.** A ticker absent
from a report (below ASIC's reporting floor, or simply not matched) gets
`current_pct: null` / `baseline_pct: null` in the dashboard JSON and "not
reported" in the email and card — same "never invent a number" rule as
Bob's results metrics. The FY-start baseline failing to resolve at all
degrades the whole run to "current data only, baseline unavailable" rather
than failing the run — the current numbers are still worth sending. The
most-recent report failing to resolve at all *does* fail the run visibly:
a plain-text failure email (`build_failure_email`) goes out naming the
reason, rather than silently skipping the week.

**Change is in percentage points, not a ratio**, and coloured the opposite
way to a price-change cell elsewhere in the codebase: red means short
interest *grew* since FY start (more bearish positioning against the
stock), green means it shrank. The two colours answer different questions
("is the stock up" vs "are more people betting against it"), so reusing the
price convention would read backwards.

**Scope is the ASX portfolio, ETFs excluded** — `tickers.yaml`'s `asx:`
section minus `etf_tickers`, reusing the same exclusion list the rest of
the repo already uses to skip ETFs for news scanning, since short interest
on an index ETF isn't the same kind of signal as on a single stock. Company
names for the email/dashboard come from `tickers.yaml` directly rather than
cleaning up ASIC's "COMPANY LIMITED ORDINARY" product strings.

**Market-wide rank and the "most shorted on ASX" callout** come from the
same report, independent of the portfolio: `rank_map` sorts every row in
the report by % short descending, so a portfolio ticker's email cell reads
e.g. "16.23% (#1 on ASX)", and the email/dashboard both lead with whichever
stock is #1 across the whole market that day — not just within the
portfolio — since that's a genuinely interesting fact on its own (DroneShield
was #1 at 16.23% on the 12-Oct-2026 report).

**Workflow (`shorty_report.yml`) runs on `ubuntu-latest`**, not the
self-hosted Windows runner — unlike SGX, this is a plain unauthenticated
file download with no TLS-fingerprint or signed-token requirement, so there
is no reason to pay the self-hosted-runner tax. Cron is `0 0 * * 0` — the
same slot Selling Sally already uses (`sunday_sally_weekly_review.yml`), so
the two run in the same weekly batch rather than adding a new time for the
user to track — plus `workflow_dispatch` with `dry_run`, `report_date` and
`baseline_date` overrides — the date overrides exist mainly for debugging
the probe logic without waiting for a real schedule to roll around.
`theo-pages.yml` lists "Shorty Short Interest" in its `workflow_run`
triggers so a Shorty run also republishes the site, same as every other
agent.

**The email leads with a curated set, not one flat alphabetical table.**
The first version listed all ~18 portfolio tickers alphabetically, most of
them "not reported" — technically complete, visually useless. It now
mirrors Bob/Slinger's results-card look (`sgx_email.py::_results_card_html`:
dark outer panel, white rounded cards with a colored header bar) for two
curated sections — **Most Shorted** (top 5 by current %, reported tickers
only) and **Biggest Movers Since FY Start** (top 5 by `abs(change_pp)`,
so a big *decrease* surfaces just as readily as a big increase) — then a
full table underneath, sorted by current % descending with "not reported"
tickers pushed to the bottom rather than dropped. Movers is skipped
entirely when the FY-start baseline is unavailable (there's nothing to
rank). The dashboard card sorts the same way for consistency.

**Live-tested**: the first scheduled/dispatched run against the real ASIC
endpoint worked — `find_most_recent_report` resolved the 12-Oct-2026 report
(799 rows) with a plain `requests` GET and no special headers beyond the
defensive User-Agent already in `_REQUEST_HEADERS`, confirming DroneShield's
16.23% from the user's own report, plus genuinely interesting real moves
(ABB's short interest went from ~1% at FY start to 6.4%).

### Wally's watchlists, under the holdings section, with a full-detail PDF attached

The first live email's flat alphabetical table of ~18 holdings (mostly "not
reported") read fine, but doing the same thing for Wally's watchlists —
~150 ASX tickers across five lists — would be an unreadable wall of
"not reported" rows in the email body. So the watchlist breakdown gets the
same curation the holdings section already had (Most Shorted / Biggest
Movers, top 5 each) as its own pair of card sections below the holdings
ones, and the **full** detail for both universes — not just the top few —
goes into a new PDF attached to the email (`shorty_pdf.py`,
`build_full_report_pdf_html`), rendered via Playwright + bundled Chromium
exactly like Bob USA's `_render_analysis_pdf` (no SGX-style fingerprint
constraint, so no need for `channel='chrome'`). Same "glance in the email,
everything in the attachment" split Bob/Slinger/Ned already use. The PDF
is the one place in Shorty's output that's allowed a `<style>` block — the
table-only-inline-styles rule in CLAUDE.md's "Email HTML constraints" is an
email-client limitation, not a PDF one.

**Watchlist tickers come from `wally.watchlist_loader`, not Wally's main
pipeline.** `load_watchlist_universe` (`shorty_fetch.py`) reuses only the
lightweight YAML loader to read Wally's five `STANDARD_WATCHLISTS`
(`wally.config`) — not `wally/main.py`, which pulls in EODHD fetches, chart
rendering and an LLM shortlist call that Shorty has no use for. Ticker ->
watchlist-name is de-duplicated in the exact priority order Wally's own
screen uses (Income > JM > Aussie Tech > Cornerstone > Nap Taker), so a
ticker on two lists is attributed to the higher-priority one, same as Wally.

**Only `.AX`-suffixed tickers survive the filter.** The watchlists
deliberately mix in non-ASX names ASIC's report can never cover — Nap
Taker holds bare US tickers (AMD, MSFT), Cornerstone holds bare UK ones
(AUTO, LSEG) — and there is no other reliable exchange marker in these
files (ASX entries carry the literal `.AX` suffix Wally's loader puts on
every ASX item; non-ASX ones never get one). Guessing from a ticker's shape
alone would be wrong often enough to matter, so only the suffixed ones are
kept, and the suffix is stripped before matching against ASIC's bare
Product Code.

**Portfolio holdings are excluded from the watchlist universe** — a
ticker that's both a holding and on a watchlist (e.g. CSL on JM Watch
List) already has its own section above; showing it twice under a
different heading would just be confusing. `run()` passes `tickers.yaml`'s
key set as `exclude` to `load_watchlist_universe`.

**Watchlist company names come from the ASIC report itself, not a new
dependency.** `tickers.yaml` only names the portfolio; the watchlist YAMLs
carry ticker codes only. Rather than add EODHD (or any other lookup) just
for a cosmetic name, `_build_watchlist_rows` reads it off whichever ASIC
report (current or baseline) already matched that ticker — `ShortRow`'s
`product` field is the company name ASIC itself publishes
("DRONESHIELD LIMITED ORDINARY"). This is free precisely where it
matters: a ticker can only land on a "most shorted" or "movers" card if
it was matched in the current report (and, for movers, the baseline one
too), so every featured card is guaranteed to have a name. A ticker in
neither report — never featured on a card, only in the PDF's full
table — has no name, same as it has no percentage; never guessed from
the ticker code.

`shorty_fetch.clean_product_name` turns ASIC's ALL-CAPS, suffix-laden
string into something readable: strips the trailing security-type
descriptor (`ORDINARY`, `FPO/UNITS STAPLED`, `ORDINARY FULLY PAID`, …),
then title-cases word by word — except a short (<=4 char) all-caps word,
left alone on the assumption it's a ticker-like acronym (`BHP`, `CSL`)
rather than a word wanting sentence casing. Imperfect at the margins
("XERO Limited" stays as `XERO`, not `Xero`) but a deliberate trade for
never mangling the acronyms that are the common case. Purely cosmetic —
never used to decide anything, so getting it slightly wrong costs
nothing. The email card (`shorty_email._card_html`) shows the name and
the watchlist badge together now, not the name-or-badge either/or the
first cut had; the PDF's watchlist table gained a matching Company
column.

**A watchlist-load failure degrades to holdings-only, never a silent
empty section.** If `load_watchlist_universe` can't import or load Wally's
lists, it returns `({}, error)`; the email and PDF both render the real
reason as a visible amber note in place of the watchlist sections rather
than just omitting them — same "half-broken must never look clean" rule
as the FY-start baseline's own degrade path.

**Dashboard JSON carries a watchlist count and error, not the rows
themselves** — `docs/data/shorty.json` gets `watchlist_count` and
`watchlist_unavailable_note` so a load failure is visible in the JSON too,
but the dashboard card doesn't render the watchlist breakdown yet (only
the email and PDF do). A future pass can wire it in if wanted.

`shorty_report.yml` now installs `playwright` + `python -m playwright
install --with-deps chromium` (same step Bob USA's workflow uses) and
uploads `outputs/shorty/` as a run artifact on a `dry_run: true` dispatch —
without that, a dry run's preview files (including the copied-out PDF)
only ever exist inside the ephemeral runner and can't actually be
inspected.

## Selling Sally — the value wedge between BUY and SELL

Sally is anchored to value, not to the share price. The 52-week high (and
Harry's broken-thesis flag) still decide *when* she looks; the **value wedge**
decides what she sees. Engine `sunday-sally/src/value_wedge.py`, chart
`wedge_chart.py`, email/memo block `wedge_report.py`.

**The corridor moves through time.** For every weekly point:
`BUY = EPS in force x BUY PE in force`, `SELL = EPS in force x SELL PE in
force`. Both inputs are time-dependent. An EPS figure applies from its
**release date** (`earnings[].date` in `valuations/<slug>.yaml`) onwards and
never before: no look-ahead, no backfilling today's EPS into history.

**Two forces, kept apart on purpose.** EPS changes shift the corridor and
leave the relative wedge (`SELL PE / BUY PE - 1`) alone; only multiple changes
move it. The chart therefore has four panels on one date axis: price vs the
corridor; actual PE vs BUY/SELL PE. Separate panels, never a dual axis. The
price is every real daily close; BUY and SELL step only on a release date
(`daily_corridor`), so they are flat for each six-month period. The corridor
is neutral grey; price below BUY is shaded green (buying zone), above SELL red
(selling zone). The x-axis is labelled by financial year (FY16 centred on its
Jul-Jun span, `fy_end_month` from the config's period_end rows). The absolute
and relative wedge panels were dropped from the PNG for simplicity (still in
the Excel workbook and CSV). Numbered markers key into a "why the
corridor moved" list ("EPS fell 49% -> corridor shifted downward",
"SELL multiple increased from 40x to 45x -> corridor widened"), so the PNG
explains itself when forwarded. 52-week highs are small markers: a review
trigger, never a value level.

**Multiple history, most authoritative first:** `multiple_history:` in the
valuation YAML; else every change to `buy_multiple`/`sell_multiple` in the
file's git history (dated by commit, so both Sally workflows check out with
`fetch-depth: 0`); else the single configured pair, labelled "never changed".
Never back-date a multiple change that was not made at the time.

**Seven deterministic diagnostics** (more valuable because of EPS? range
wider? price faster than value? in the wedge? above SELL? BUY up because of
EPS or the multiple? genuine stretch or just a 52-week high?) are computed in
code, printed in the email/memo and handed to Claude as facts. Claude's
`VALUATION STATUS` is now BELOW BUY / INSIDE THE WEDGE / ABOVE SELL.

**Price above SELL is a trigger of its own.** `classify_alert(wedge=...)`
returns Tier 2 when the price is above SELL even far from a 52-week high, and
counts it as a stretch signal when near one. No wedge (no valuation YAML) means
behaviour exactly as before.

**On demand: `sally_wedge.yml` ("Sally Wedge Check").** `workflow_dispatch`
with `tickers` (comma/space separated, `.AX` assumed). Sets `SALLY_TICKERS`;
`main()` runs every named ticker through the full pipeline whether or not a
trigger fires (tier "On demand: no trigger"), emails the wedge chart, CSV and
memo, uploads them as a run artifact, and **never** writes
`docs/data/sally.json` or Drive — same one-off rule as Bob's ad-hoc modes.

**No made-up EPS. Annual from SWS, halves only when reported.**
`valuations/<slug>.yaml` `earnings:` is generated from the Simply Wall St
export: `cd sunday-sally && python -m src.sws_import <SWS_Data.xlsx> --ticker
PWH --write` (`src/sws_import.py`). SWS dates are **Unix timestamps** (seconds
since 1970-01-01 UTC; Excel `=A1/86400+DATE(1970,1,1)`). It takes
`past_earnings_per_share_ltm_history` (annual, offset 0 = year ending
`past_last_earnings_update_annual`), dates each year by the first SWS
dividend date after year end (on or a few days after the results; checked
against PWH FY23/FY25/FY26) or, if none, the ASX two-month deadline: late is
safe, early would be look-ahead. SWS has no half-year EPS. Halves go in
`half_year_eps:` by hand with a source; a TTM point at a half-year release
(`FY{Y-1} - 1H{Y-1} + 1H{Y}`) is made only when all three are reported, and
every missing half is listed on the chart and in the email. ASX reports
six-monthly: never quarterly numbers. Business context per period lives in
`period_notes:` so a re-import does not wipe it. PWH: FY16-FY26 from SWS
(export 261003), 1H25 and 1H26 from SWS's results news; 1H16-1H24 missing.

**Foreign-currency EPS (BHP).** `eps_currency: USD` in the valuation YAML
means `ttm_eps` is US cents, converted to the share price's currency ONCE, at
the rate on the result's release date (EODHD `USDAUD.FOREX`). BUY and SELL must be
flat between results (ASX reports six-monthly); an earlier version converted
at each week's rate and the lines sloped with the currency, which JM rightly
rejected. Diagnostics still split EPS change from FX change. Reported figures SWS
lacks go in `extra_eps:` (source required, e.g. the company's results
release); a period whose basis does not reconcile goes in `eps_exclude:` with
the reason. SWS's LTM series is anchored on `past_last_earnings_update`, which
is a half-year end when the last result was a half (BHP: Dec, labelled
`1H{FY} TTM`); release dates are the earlier of SWS's dividend date and the
ASX two-month deadline (both on or after the real release). The chart shades
"No EPS in the data" and "Loss: no PE-based value" instead of leaving silent
gaps, and lists every missing FY/1H. The legacy value-chart workbook refuses a
config with foreign-currency EPS rather than mislabel it.

**Smoothed (through-the-cycle) EPS for cyclicals.** `eps_smoothing: {years:
5, exclude: [FY2016]}` in a valuation YAML (BHP) sets each result's
`norm_eps_cents` to the plain average of the reported 12-month EPS figures
released in the previous N years, as known on that release date (no
look-ahead), held flat until the next result. Excluded periods (one-offs like
Samarco) are left out of every average. The BUY/SELL corridor, zones, alerts
and diagnostics then run on smoothed EPS; the chart keeps the statutory
corridor as faint dashed lines and shades statutory losses. Earlier reported
years (BHP FY10-FY13 in `extra_eps`) only feed the window.

**Fair value is not the middle of the wedge.** `fair_split` (default 0.3)
puts fair value 30% of the way from BUY to SELL: JM buys well below value and
sells well above it (BHP 13x/20x -> fair 15.1x, matching a 14-16x
justified-PE check). Drawn as a dashed line, in the headline and on the
right-edge labels; `fair_split: null` turns it off.

**Depressed statutory earnings (PWH).** `depressed_earnings: [{start, end,
label, reference_period}]` shades a period where statutory EPS understates
earning power (PWH's Brisbane relocation: double running costs, low
utilisation of the new site) and draws a faint dotted reference corridor on
the named normal year's reported EPS (FY24). The wedge itself stays on
statutory EPS: no smoothing for a non-cyclical. PWH framework (Oct 2026): BUY
25x / SELL 50x, `fair_split: 0.35` -> fair ~34x = PWH's own median PE FY16-FY24.

**52-week P/E and P/FCF in the email.** Every flagged company gets two
range bars in Sally's summary table (52W P/E, 52W P/FCF) and a small inline
PNG (`ranges_52w.png`, shown at 560px) with one panel per multiple: daily
line over 52 weeks, low/high reference lines, current dot, dotted lines on
result release dates, and labelled gaps ("n/m: negative FCF") instead of
invented values. Data and maths in `shared/ranges.py`, picture in
`shared/range_chart.py`. TTM net income and FCF are summed from EODHD's
half-year (or quarterly) statements, divided by the checked share count, and
counted from each release date; EODHD's rounded `epsActual` is not used (it
made PWH 82x instead of 55x). This is statutory EODHD P/E, so it can differ
from the wedge's P/E for names whose valuation YAML uses smoothed or
hand-entered EPS (BHP). `ranges_52w` (without the daily series) also goes
into `docs/data/sally.json`.

**`buy_multiple: archetype`.** A valuation YAML may hand its BUY multiple to
the archetype rules instead of typing a number (ARB first, Oct 2026): Sally
(`_apply_archetype`) and Wally's value chart both resolve it through
`shared.classifier.classification_for`, and an `avg_Ny` EPS basis turns on
N-year smoothing of the annual EPS. SELL stays a number in the YAML.

**Every holding gets a wedge unless it can't have one (Oct 2026).** A holding
with no `valuations/<slug>.yaml` gets an automatic config (`value_wedge.auto_config`):
statutory annual EPS from EODHD (`shared/eps_history.py`, NPAT / checked share
count, from the release date), the archetype BUY multiple, and SELL from
`sell:` in `config/valuation_archetypes.yaml` (the stock's own 10-year median
P/E, clamped to 1.5-3x BUY; `classifier.sell_multiple_for`). A YAML can opt in
piece by piece: `earnings_source: eodhd` replaces hand-typed `earnings:`,
`sell_multiple: auto` uses the same SELL rule. No wedge when the archetype has
no P/E line (early_growth: pre-profit) or EODHD has no profitable years; the
email says which, in one short line. BXB/CPU/CSL/NHC/RMD/WDS had invented
"Est." EPS rows; they now read EODHD. SEK/VHY (not holdings) still do.

**One-year forecast from consensus.** With no `forecast:` block (and no
`auto_forecast: false`), the wedge draws EODHD `/calendar/trends` consensus
EPS (`eodhd.consensus_eps`) for the fiscal years after the last reported one,
labelled consensus with the analyst count. An assumption, never a zone or alert input.

**Attachments: one PDF + one workbook per company.** `wedge_pdf.build_report_pdf`
(matplotlib PdfPages, no HTML engine) puts a cover table, each wedge chart, the
52-week ranges and the memo in one PDF; charts stay inline in the email. The
workbook's first chart is a native Excel look-alike of the wedge (stacked area
for green/grey/red zones + forecast band, lines on the same axes, FY date
axis). It has no numbered event markers or right-edge labels: Excel can't do
those honestly, so the PNG/PDF stays the reference. Range notes are pruned
to the 52-week window and at most two show under the chart.

**The latest point uses the multiples in force today**, so a framework change
made at the weekend (WDS 9x/14x -> 9x/16x, 2026-10-18, in `multiple_history`)
shows on this week's numbers without back-dating history. WDS smoothing
excludes the FY2015/FY2020 impairment years.

**How many years' low, at the top of the chart.** `low_line` (data in
`shared/lows.py`, shared with Wally's multi-year flag): within 5% of the
1/2/3/5/10-year low, and the lowest close since when. Also in the email.

**Forecast cases and the case each way.** `forecast: {cases: [{label, basis,
rows}]}` draws one band + fair line per scenario (e.g. Recovery = consensus vs
No recovery = trend), on the wedge's own EPS basis (smoothed when the wedge
is). `outlook: {recover: [...], not_recover: [...]}` prints two columns of
bullets in Sally's email and feeds Claude's prompt. Both are assumptions and
research, never used for zones or alerts.

**Your buys and the start date.** Buy dates come from the IRR ledger
(`data/decisions.json`, dates only) as green markers and numbered events.
`start` (workflow input / `SALLY_WEDGE_START` / `--start`): `full`,
`year_before_buy` (365 days before the first buy) or a date; prices are still
fetched a year earlier so 52-week highs are real at the left edge.

**Editable outputs.** Every wedge run writes, per ticker:
`wedge_chart.png` (matplotlib, `wedge_chart.py`), `wedge_chart.svg` (same
figure, `svg.fonttype: none` so text stays text: editable in PowerPoint via
Convert to Shape, Illustrator, Inkscape, Figma), and `value_wedge.xlsx`
(`wedge_workbook.py`): four **native Excel charts** on a Weekly sheet whose
EPS/PE/BUY/SELL/zone columns are formulas reading the EPS and Multiples
sheets (`LOOKUP(2,1/((dates<=A2)*(vals<>"")),vals)` = latest figure released
by that week; ignores blank spare rows). Prices are values. Verified by
recalculating in LibreOffice: every weekly row matches the Python engine.
Locally, without email: `python -m src.wedge_cli PWH [--prices-csv f.csv]`.

## GitHub Pages — one publisher, triggered by the agents

The site at `https://johnnym77.github.io/Reporting-Agent/` has two halves that
share one deploy: the combined agent dashboard (`docs/index.html`, generated by
`scripts/build_dashboard.py`) at `/`, and Theo's slides at `/theo/`. A Pages
deploy replaces the entire site in one shot, so both halves must be built and
uploaded by the same workflow. `.github/workflows/theo-pages.yml` ("Publish
site") is that workflow, and it is the only one allowed to deploy. A second
workflow publishing either half on its own would silently delete the other.

### Pages source must be "GitHub Actions"
Settings → Pages → Build and deployment → Source. Anything else breaks the
site, and the two failure modes look nothing alike:

- **Deploy from a branch, `main` / `(root)`** — Jekyll finds no `index.html` at
  the repo root and renders `README.md` instead. The site turns into a plain
  README page. This is what "the styling disappeared" looks like.
- **Deploy from a branch, `main` / `docs`** — the dashboard renders correctly,
  but `/theo/` 404s. `site/` is in `.gitignore`; Theo's slides only ever exist
  inside a CI run, so a branch deploy cannot see them.

Neither can be fixed from the repo — it is a settings toggle. Flipping it back
to "GitHub Actions" then re-running the workflow restores the site.

### Why the deploy hangs off `workflow_run`, not off a commit
Bob, Ned, Wally and Sally each write their own `docs/data/*.json`, re-run
`build_dashboard.py`, and commit `docs/index.html` with **`[skip ci]`**. That
tag is what keeps four agents from triggering each other into a loop — and it
also stops the Pages workflow from ever seeing those pushes. The result was a
site frozen at the last thesis change while `docs/index.html` moved in git
every morning: Bob ran, the email arrived, the website did not move. Nothing
looked like an error, which is what made it expensive to spot.

Adding `docs/**` to the `push` paths does not fix that on its own — `[skip ci]`
suppresses the event before any path filter is consulted. So the workflow
listens for the agent *runs* completing instead:

| Trigger | When |
|---|---|
| `Daily Announcement Digest` (Bob) | daily, 22:13 UTC (9:13am AEDT) + 23:43 UTC catch-up |
| `Ned News Agent` | daily, 23:30 UTC |
| `Wally Watchlist Screening` | Friday, 22:30 UTC |
| `Selling Sally Weekly Review` | Sunday, 00:00 UTC |

Two details this depends on. `workflow_run` only fires for workflows defined on
the default branch, so these triggers do nothing until the change is merged to
`main`. And `github.sha` on a `workflow_run` event is the default branch's tip
as of when the event fired, which can predate the dashboard commit the
triggering run made moments earlier — the checkout pins `ref:` to the branch
name (`TARGET_BRANCH`) so the deploy always carries the newest data.

The trigger is not gated on the agent run succeeding. A run that emailed its
digest and then tripped over on a later step has still committed data worth
publishing, and re-deploying unchanged content costs nothing.

## Harry Hindsight — the Chief Sceptic (`hindsight/`)

Sits above Bob, Sally, Wally and Theo. Reads their existing outputs
(`docs/data/{sally,bob,wally}.json`, `theses/` + git history,
`data/decisions.json`, `watchlists/jm_watchlist.yaml`) through adapters in
`hindsight/adapters.py`. It never imports or modifies those agents, and every
existing agent must run exactly as before if Hindsight is disabled or broken.
Full design and assumptions: `docs/CAPTAIN_HINDSIGHT_ARCHITECTURE.md`.

**Reads Theo, never writes it.** Thesis files are Theo's. Hindsight records
its findings (and "Questions for Theo") in its own case files.

**Personal data never committed.** Case files, `hindsight.db`, reports, the
bias profile and responses go to `HINDSIGHT_STORE=local` (`hindsight_data/`,
gitignored), which the workflow carries between runs in the Actions cache
(restore at start, save at end, same pattern as Bob's `state_seen.json`).
This is the default. `private_repo` (a checkout of a separate repo at
`HINDSIGHT_PRIVATE_REPO_DIR`) still works if chosen by hand, but that repo was
never created: 45 automatic runs (2026-09-24 to 10-07) failed at its checkout
step while only manual `store=local` runs went green.
`store.open_store` refuses any directory the public repo would track, and a
misconfigured `private_repo` raises `StoreConfigError`; there is no fallback.
Workflow logs print counts and statuses only, because Actions logs on a public
repo are public. `config/hindsight.yaml` holds rules and thresholds, never
positions.

**No silent placeholders.** Every analysis ends `OK`, `SKIPPED_CAP`,
`FAILED_API` or `FAILED_INVALID`, and the email renders the three non-OK
states differently with the real error. Same lesson as Bob's canned-analysis
incident: a half-broken digest must never look like a clean one.

**Deterministic first, model second.** No gate, no call. JM Watch List names
with nothing new show `NO CHANGE` at zero cost. `HINDSIGHT_MAX_LLM_CALLS`
(default 10) caps a run; overflow is queued in the store and run first next
time. One validation retry per analysis, with the error attached.

**The model proposes, code decides.** `validators.py` downgrades FACT claims
with no source ref, bias states without a ref to a real record (to UNKNOWN),
PRESENT 7 Powers with only management evidence, and any LOLLAPALOOZA that fails
the three-part gate. It never raises a severity. Warnings without a
falsifiable prediction are dropped. Behavioural facts (average cost, tranches,
averaging down, sell target, weights, unanswered Sally flags) are computed in
`behaviour.py`, never by the model.

**Sally never says SELL.** Her verdicts are `Trim candidate` / `Hold but stop
adding` / `Watch only`. The adapter maps Trim to REDUCE, and Tier 2 to REDUCE
only at the top of the valuation range near the 52-week high (thresholds in
config). `python -m hindsight sell TICKER` forces a sell review regardless.

**Triggered by the agents it reads, not a clock.** `captain_hindsight.yml`
listens for `workflow_run` completion of Bob, Wally and Sally (no cron). The JM
triage is guarded to once a day (`triage_done` in the store) so Bob's catch-up
run cannot re-triage and re-email. Only fires from `main`.

**A close burst of those completions is not free, so it's debounced.** The
trigger fires on every completion of Bob/Wally/Sally, including a stood-down
catch-up run that sent no email but still reran `build_dashboard.py` and
committed a one-line diff. On 2026-10-09/10 two real Bob fires (its DST-safety
crons can both land in one morning once GitHub's scheduler delay pushes them
together) plus one Wally fire triggered three Harry runs in ~40 minutes;
`concurrency: { group: captain-hindsight, cancel-in-progress: false }` queued
them instead of deduping, so each ran its own multi-minute LLM review and
tried to commit `docs/data/harry.json` — two of the three collided on that
file and failed with a merge conflict mid-rebase. `cancel-in-progress` is now
`true`: a newer trigger cancels a still-queued/in-progress Harry run instead
of racing it, collapsing a burst into one completed run.

**Output mirrors Bob.** `hindsight/email_html.py` builds a table-only,
inline-styled card per report (a test bans flex, grid, `<style>` and
`class=`), and a weasyprint PDF per OK report attached to the email. The PDF
may use a stylesheet; the email may not.

**On the public site.** Each run writes `docs/data/harry.json`
(`hindsight/web.py`): severity, verdict, thesis read, the would-buy / would-rebuy
answers, what would change the call, and (both switched on in
`config/hindsight.yaml`) the evidenced biases and the position as percentages
only. The Harry
workflow commits it and rebuilds `docs/index.html`; "Publish site" listens for
"Harry Hindsight" completing.

**Harry hands broken theses to Sally: `data/harry_flags.yaml`.** When a
Harry review of a holding reads the thesis as BROKEN (the model's thesis test,
or the git-history detector), `hindsight/flags.py` writes the ticker there;
THESIS INTACT or STRENGTHENED removes it, WEAKENED/CHANGED leave it. Sally
(`sunday-sally/src/harry_flags.py`) loads it every run and forces a full sell
analysis on each flagged holding even when her near-high screen does not fire
(`apply_harry_flag`: tier "Harry: thesis broken" unless her own tier fired,
verdict "Sell review: Harry says thesis broken", hold/trim/exit prompt). That
verdict reads as SELL to Harry's Sally adapter, so the Harry run that follows
each Sally run re-checks every flagged name. Ticker, date and verdict only in
the file: it is public. Editable by hand.

**Thesis ledger: Harry reads, Theo records, Sally sells.** `mode=sweep` reviews
every holding with a live thesis. Each OK holding review rewrites that ticker's
row in `docs/data/harry_theses.json` (thesis read, pillar statuses, evidenced
Munger tendencies, % vs cost, % of book). A BROKEN row becomes a Theo question
(`theo.signals.from_harry`, answered by a `trigger: HARRY_BROKEN` review) and
a `data/harry_flags.yaml` entry that Sally turns into a sell review. **Never a
dollar amount** gained or lost, and no average-cost price, in anything public;
percentages are fine. Tests assert it.

**Needs full git history.** Thesis versions and Sally's consecutive-flag streak
come from `git log`; the workflow checks out with `fetch-depth: 0`.

**The test suite leaves the working tree alone.** It used to rewrite
`docs/data/wally.json`, `fundamentals/` and `valuations/`; those tests now run
in tmp dirs. `git status` after `pytest` should be clean, and if it isn't,
that's a test bug.

## Prompt caching (shared/llm.py, 2026-10)

On for every agent by default; `LLM_PROMPT_CACHE=0` turns it off. `send()`
marks the system prompt as a cache breakpoint, so the second and later calls
with the same prompt inside five minutes (Bob's results prompt across a
reporting-season morning) read it at ~10% of the input price. On a
continuation (`len(messages) > 1`: Harry's and Esther's JSON-repair retry,
Esther's web-search hand-backs) it also adds automatic caching on the tail.
A first-turn PDF is deliberately not cached: it is never re-sent, and a cache
write costs 1.25x. Prompts under the model's minimum cacheable size (it
varies by model) are silently not cached. Bob logs
`[llm] <model>: in / cached / written / out` per call to show hits.

## Message Batches (shared/llm.py, 2026-10)

Half price, not instant. Off unless `LLM_BATCH=1`, which only Wally, Sally,
Harry and Ned's news scan set, and only on automatic runs
(`github.event_name != 'workflow_dispatch'`): a manual run goes direct.
Bob, Slinger, USA, Esther, Ned transcripts and Results Pack never batch,
because someone is waiting on them.

`send()` with batching on submits a one-request batch and waits; `send_many()`
puts several independent requests in one batch (Ned's headline summaries via
`llm_summarise_all`). **Never fewer answers than a direct call:** a request the
batch returns as errored/expired/canceled, a batch that fails to submit, and a
batch still running when the wait cap is hit (cancelled) are all re-sent
direct, so a real API error still raises the same exception the agent already
handles. Waiting is capped per process by `LLM_BATCH_MAX_WAIT_MIN` (30 in the
workflows); once spent, the rest of the run goes direct, so a slow batch day
costs at most that many Actions minutes. Batch requests use a 1-hour cache TTL
on the system prompt, since consecutive batches can be more than five minutes
apart. Logs: `[llm/batch] submitted / ended after / sending direct`.

## Ned transcript digests: portfolio-aware (YouTube + podcast)

`run_transcript_digest` / `run_podcast_digest` (`ned/main.py`) share
`_digest_and_deliver`: save transcript, load portfolio context, one
analysis call, PDF, email, `docs/data/transcripts.json`. The daily news scan
(`run_scan` / `llm_summarise`) is untouched and stays on Haiku.

**Portfolio context** (`ned/portfolio_context.py::load_portfolio_context`)
builds a plain-text block from `tickers.yaml` (VAS/VEU/VHY marked ETF),
`theses/*.md` frontmatter only (skips `draft: true`; pillar claim, status and
kill condition, never evidence) and `watchlists/*.yaml` (`.AX` stripped;
`tii75_watchlist.yaml` only while under 40 names). Capped at ~25k chars by
shortening each thesis's `the_bet`; tickers, claims and kill conditions are
never trimmed. Fails soft on any missing or malformed file, reads UTF-8
explicitly (Windows runner), and logs its final size.

**The analysis** (`ned/transcript_digest.py`) asks for strict JSON; the
parser strips fences, recovers an object wrapped in prose, and otherwise
keeps the reply as markdown (`Unrated`). A reply cut off at max_tokens, an
API error or a missing key is a failure: subject `Ned [Digest failed] ...`,
the reason on the email and the PDF cover. Transcripts over
`NED_TRANSCRIPT_LLM_MAX_CHARS` are never clipped: each ~150k-char part is
reduced to extraction notes and the digest runs on the notes.

| Env | Default |
|---|---|
| `NED_TRANSCRIPT_MODEL` | `claude-sonnet-4-6` |
| `NED_TRANSCRIPT_MAX_TOKENS` | `6000` |
| `NED_TRANSCRIPT_LLM_MAX_CHARS` | `400000` |

All three are optional repo variables wired into both Ned transcript
workflows. `transcripts.json` entries now carry `digest_json`,
`portfolio_relevance`, `digest_error`, `channel` and the real title (YouTube
via oEmbed, falling back to the video ID).

**The PDF** (`ned/transcript_pdf.py`) must render the same on weasyprint
(ubuntu) and Playwright + Chrome (Windows): tables and block layout only,
system fonts, geometry in `@page` (`:first` zero margin for the full-bleed
cover, `@bottom-center` running footer). Playwright passes

## Ned's news scan: source tiers, target sites, newsletters

**Kalkine flooded the feed because Ned couldn't see the publisher.** Google
News tags every item `<source url=...>Kalkine Media</source>`; `_fetch_rss`
ignored it. Kalkine machine-rewrites every ASX announcement into headlines
full of "buy-back", "revenue", "results", so keyword scoring ranked it
CRITICAL and it took both of a company's dashboard slots. Now `publisher` /
`publisher_url` are captured (title suffix " - Publisher" as fallback, stripped
only on Google News items so a static feed's "buy - or sell?" survives).

**Tiers, not a block** (`ned/source_quality.py`, lists in
`media_sources.yaml: source_tiers`). Tier 3 (Kalkine) is capped at LOW in
`importance_scorer._adjust_for_source`, skips the Haiku summary, and is
collapsed into one "Wire rewrites" line per publisher at the bottom of the
email. Never on the dashboard. `kalkine` is forced into tier 3 even if the
config list is emptied. Tier 1 gets +1 only when the headline already scored.
Unlisted = tier 2. A static feed can pin its tier with `tier:`.

**Same story, several outlets** collapses to the best tier
(`collapse_duplicates`, 60% headline-word overlap or identical URL, per
ticker), recorded as "Also covered by". The collapsed copies' seen keys ride
on the winner (`merged_seen_keys`) so they don't resurface alone tomorrow.

**`[not material]` was a no-op.** The summary was only stored when it was
*not* "[not material]", then filtered against that same dict, so nothing was
ever filtered. It now sets `not_material` and demotes to LOW (kept in the
email, off the dashboard) rather than dropping.

**Target sites** (`type: google_news_sites`): one extra Google News query per
company, `("Brambles" OR "ASX:BXB") (site:livewiremarkets.com OR ...)`, no
context terms. Gets headlines from paywalled sites and from sites whose own
feeds block bots (Livewire and Stockhead both refused a fetch in Oct 2026).
`_matches_company` also accepts exchange-prefixed codes (`ASX:BXB`,
`ASX: BXB`); a bare code never matches (CAT, IAG are words).

**Newsletters** (`ned/newsletter_scanner.py`, `media_sources.yaml:
newsletters`). Kestrel Run (Australian defence brief) publishes each issue
publicly at `kestrelrun.com/briefs/YYYY-MM-DD`, so `web_archive:` is the
primary route and needs no credentials. Gmail IMAP (read-only, `BODY.PEEK`,
All Mail) is the backup and the route for email-only newsletters:
`NED_IMAP_USER` / `NED_IMAP_PASSWORD` (Gmail app password), falling back to
`EMAIL_FROM` / `EMAIL_APP_PASSWORD`. An emailed issue whose date was already
read from the web is dropped. Confirmation/welcome/receipt mail is skipped.
Each paragraph naming a holding becomes a normal tier-1 hit; `digest: true`
adds one Haiku read of the whole issue against the portfolio and `watch:`
themes, which catches indirect items (a counter-drone tender for DRO). The
prompt marks the newsletter body as untrusted. Inbox failures and
not-configured (when some newsletter has no web archive) show as a red line
in the email: never a quiet empty section.

**Checking sources:** "Ned News Agent" -> Run workflow -> `probe_only`, or
`python scripts/ned_probe_sources.py`.

## Tests: stub a dependency only if it's missing

Test files that import agent code stub optional third-party modules through
`tests/_stubs.py::stub_missing(...)`, which installs an empty module only when
the real one isn't installed. Never write `sys.modules[name] =
types.ModuleType(name)` at import time: that stub lives for the whole session
and silently breaks every later test that needs the real library. It hid 40
Wally failures (depending on collection order) and let Results Pack tests skip
code they were supposed to exercise. `pytest tests` passes in any order and
file by file; keep it that way.


## Esther the Wrestler: SWS Narrative + valuation editor (`esther/`)

Sits above Bob, Wally, Sally, Harry and Theo like Harry does: reads their
`docs/data/*.json`, `theses/`, `valuations/` and `data/decisions.json`, and
never imports or modifies them. Manual only (`esther.yml`, workflow_dispatch);
modes `full`, `quick`, `valuation`, `thesis`, `challenge`. Design notes live in
`esther/README.md`.

**One Narrative case, not bear/base/bull.** SWS has one set of sliders and the
narrative is public, about stocks JM owns. The model returns one owner's case
(growth from guidance/consensus, margin from the better years or ex one-offs,
P/E from the stock's own multiple) plus a private stress case. The first version
weighted bear/base/bull 25/50/25 on mid-cycle margins and compressed multiples;
every holding came out 20-45% below the price and read like a sell note, which
is not what JM publishes. The public copy is checked for trimming/selling/
position-size talk (`quality.private_talk_found`); that stays in the private
sections.

**The model proposes, code decides the numbers.** The value, the upside and the
reverse-DCF are computed in
`esther/valuation.py` using the SWS Narrative formula, so JM's SWS screen and
Esther's email agree. SWS ignores dividends; the dividend add-on is shown on
its own line and never folded into the SWS-comparable number.

**Holdings come from records, not the model.** `context.portfolio_status`
decides OWNED / WATCHING / SOLD from the ledger and thesis status, and the
disclosure line is appended in code, only for real holdings.

**Public repo rules apply.** Narratives and previous runs contain JM's views,
so they go to email and to `ESTHER_STORE_DIR` (gitignored `esther_data/`, or
the private repo in Actions). `store.store_dir` refuses a tracked path.
`tests/test_esther.py` uses a synthetic fixture, not a real narrative.

**Email is table-only HTML** like every agent email; a test bans `<style>`,
`class=`, flex/grid and em dashes in the output.

## Micky's Macro: structural trends and investment intelligence (`mickys_macro/`)

Sits above Bob/Wally/Sally/Theo exactly the way Harry and Esther do: reads
their existing outputs read-only, never imports or calls the agent that
produced them, and runs (or is disabled) without touching anything else.
Full design and the Phase-1 repo inspection it was built from:
`docs/MICKYS_MACRO_ARCHITECTURE.md`.

**Finds long-horizon (5-20 year) structural trends from four priority
research newsletters, maps them through to candidate companies, and never
collapses the result into one buy/sell flag.** The brief's own distinction
holds everywhere in this code: an attractive macro trend, an attractive
industry, an attractive company and an attractive investment at today's
price are four separate text fields (`InvestmentFilter`), not one score.
The ten-dimension scorecard (`scoring.py`) is a vector for the same reason
-- nothing ever averages the ten into a combined conviction number.

**Gmail ingestion is read-only IMAP, same mechanism Ned's newsletter
scanner already uses** (`gmail_ingest.py`, deliberately not importing
`ned.newsletter_scanner` -- each agent owns its own small amount of IMAP/MIME
code, same "no coupling" choice as Slinger vs. ASX Bob). `readonly=True` and
`BODY.PEEK` mean nothing is ever marked read, moved or deleted; there is no
code path in this module that could write to Gmail. Dedup is on the Gmail
Message-ID via the local store, so a re-run or an overlapping lookback
window never creates a duplicate record. Sender addresses in
`config/macro_sources.yaml` were discovered by searching Johnny's real
mailbox for each of the four sources (Citrini Research, Ray Dalio/Economic
Principles, Scott Galloway/Prof G, Chamath Palihapitiya) -- never invented.
Prof G's several sub-newsletters all arrive as `profgmedia+<sub>@substack.com`
plus-addresses; one `sender_local_prefix` rule catches all of them rather
than listing each sub-newsletter by hand.

**Research content never touches the public repo.** Raw email text and
extracted claims live in `mickys_macro_data/` (gitignored, same pattern as
`hindsight_data/`/`esther_data/`), carried between runs via `actions/cache`.
`store.py` duplicates (rather than imports) Harry's "refuse a tracked path"
safety check so this agent has no import-time dependency on `hindsight`.
Only the public-safe summary (`docs/data/mickys_macro.json`, scrubbed through
`shared/public_safety.scrub_obj`) is committed.

**Four processing states, same discipline as Harry's
OK/SKIPPED_CAP/FAILED_API/FAILED_INVALID.** A truncated claim-extraction or
dossier-synthesis reply never gets bracket-closed into something that would
render as a clean result -- it stays `FAILED_INVALID` and says so, same rule
Bob/Slinger/Harry all enforce for exactly the same reason (a half-broken run
must never look like a clean one).

**Valuation numbers are never written by the model.** The LLM call that
builds a company candidate (`company_mapping.py`) is told explicitly not to
state a current price or multiple as fact; `resolve_valuation` then pulls
real figures from `shared/eodhd.py` -- the repo's only market-data source --
and anything EODHD doesn't cover for that ticker (SGX, an unresolvable name)
renders `not_covered_reason`, never an estimate.

**Hands Wally a proposal, not a merge.** `wally_adapter.py` writes
`watchlists/macro_candidates_proposed.yaml` in the exact schema
`wally/watchlist_loader.py` already reads, but it is deliberately **not**
added to `wally/config.py::STANDARD_WATCHLISTS` -- Wally does not screen it
until Johnny copies entries (with a considered buy price) into a real
watchlist. Likewise, no ticker is added to `tickers.yaml` automatically:
that would silently widen what Bob/Shorty monitor and email about every day.
Both are flagged as decisions for Johnny, not done silently -- see the
architecture doc's "what needs a decision" section.

**Research-house monitoring (Bridgewater, PIMCO, BlackRock, ...) is a
registry, not a live scraper, in this pass.** `config/macro_sources.yaml`
lists them so scoring/sourcing has a controlled vocabulary of institution
names, but no credentials or paywall-bypass exist for any of them --
explicitly left for a later pass rather than silently skipped.

## EODHD data
Before writing or changing any code that calls the EODHD API, read .claude/skills/eodhd-api/SKILL.md and the relevant endpoint doc in .claude/skills/eodhd-api/references/endpoints/. Use the exact endpoint paths, parameter names, and response field names documented there. Never guess an endpoint or field name. ASX tickers use the .AU suffix.

### EODHD is the only market-data source (2026-10)
Every share price, FX rate, dividend, PE/EV/yield and EPS figure any agent
uses comes through `shared/eodhd.py`. yfinance, Alpha Vantage and FMP are
gone (`wally/alphavantage.py` deleted, `yfinance` out of every install).
`tests/test_eodhd_only.py` fails if one comes back, or if a workflow that
reads prices loses `EODHD_API_TOKEN`.

**No fallback, no placeholder.** If EODHD has no figure the agent shows
n/a / "no price from EODHD (reason)". Wally's value chart used to draw a
*synthetic* sine-wave price series when yfinance failed; that is removed and
the build now raises. Sally's "historical PE" used to divide ten years of
prices by *today's* trailing EPS; it now uses the EPS in force each month.
Esther still falls back to her research's sourced price when EODHD has no
quote, but labels it "NOT verified".

**Who uses what.** Wally: `price_summary` (last close + 52w range of raw
closes), `snapshot` (PE, fwd PE, EV/EBITDA, P/S, div yield, FCF yield),
`fundamentals_store` (annual EPS + dividends, cached in `fundamentals/`),
value chart prices (adjusted close). Sally: price, valuation, historical PE,
value-wedge daily closes and `USDAUD.FOREX`. Harry: last/prev close. Esther:
price, shares, FX. Slinger, Ned and Theo fetch no prices, and Bob fetches none
for its results numbers (those come from the company's own PDF, the primary
source) — the one exception is `debt_profile` on the capital/debt-raise path,
which reads the latest reported balance sheet for a prior-leverage baseline
(best-effort; see the Bob fundraising-card note).

**Derived figures are arithmetic on EODHD numbers, never estimates.**
Annual EPS = income-statement net income / shares on issue at the balance
date (statutory). Checked on PWH: FY23 21.7c, FY24 24.7c, FY25 9.7c, FY26
17.8c, matching the reports. EODHD's own `Earnings::Annual.epsActual` for
ASX names is rounded to 2dp, has gaps and mislabels TTM as annual (PWH
"FY25 0.18"), so it is not used. Each EPS figure is usable from EODHD's
`reportDate`, else the two-month deadline after year end (`known_from`).
A "reportDate" on or before the year end (BHP FY03-FY13) is a placeholder
and is ignored.

**Share counts are checked, not trusted.** EODHD has two: `outstandingShares`
and the balance sheet's `commonStockSharesOutstanding`. A year is left out of
`annual_eps` (shown as NOT USED in the data check) when they disagree by more
than 20%, when they move inconsistently year on year (one +50% or more, the
other not), or when a single source jumps 50%+. Rolls-Royce FY17-FY20 fail:
EODHD's Dec-2019 count was ~5.6bn against ~1.9bn on issue, turning a -69p
year into -23p. A real rights issue both sources agree on is kept.
`fundamentals_store.PROVIDER_VERSION` forces caches built under older rules
to rebuild.

**Coverage gaps are explicit.** EODHD has no SGX, NZX or Tokyo feed on
this plan: `eodhd.symbol()` raises `EODHDNotCovered` rather than borrowing
another source. LSE prices are pence (GBX), same as Yahoo's `.L`.

**Hand-entered data still wins.** `valuations/*.yaml` (Sally's SWS-imported
and half-year EPS, Wally's `series:` overrides) is sourced from company
reports and overrides EODHD. A `fundamentals/*.json` cache written by any
earlier source is treated as stale and rebuilt from EODHD.

**Checking the numbers.** Actions -> "EODHD Data Check" (`eodhd_check.yml`)
runs `scripts/eodhd_check.py` and puts a table of every figure the agents
will use (and, with `detail`, the EPS working year by year) on the run's
Summary page. Locally: `python scripts/eodhd_check.py PWH --detail`.
